Preface

It is possible to analyse data in R without thinking much about programming. You import a dataset, fit a model, create a figure and report the results. This is often sufficient for one analysis. But what if you need to repeat the same calculation for a hundred variables? Or write a small simulation? Or investigate an unfamiliar object returned by a package?

This script is about the next step: from using ready-made commands to understanding how to program in R. It was developed from years of teaching notes, programming exercises and experiments with different solutions to the same problems.

I have tried to follow a simple teaching principle: start with what the reader already knows. First solve a problem in the most straightforward way. Then ask how the solution could be reused, extended, checked or made faster. Advanced ideas are valuable when they explain a real problem; they are less helpful when introduced merely to show off a language feature.

0.1 Who is this for?

The intended readers are students and researchers who have already performed a few analyses in R. You should recognise assignment (<-), a vector, a data frame and simple functions such as mean() and plot(). No prior knowledge of formal programming theory, environments, S3 or functional programming is assumed.

Most examples use base R. The graphics chapter compares Base R, lattice and ggplot2, and some optional examples mention established statistical packages. You can read the main chapters without installing a large collection of dependencies.

0.2 How to use the script

Many examples deliberately show several possible solutions for one task. Do not assume that the shortest or most sophisticated solution is always the best. Instead ask: Does it work? Do I understand it? Is it easy to adapt? How will I store the result? What happens if the input changes?

Comments inside the code explain what individual statements do, particularly in the early chapters. The surrounding text explains why a solution is chosen and when it may be preferable to an alternative.

Unless otherwise noted, copy each example into a fresh R session and run it from top to bottom within its section. An example preceded by # is a comment and will not be executed until you remove the comment marker. Some examples intentionally illustrate errors; these are marked clearly.

The manuscript does not automatically execute R during rendering. The code has been reviewed editorially, but it has not been comprehensively run against an installed R interpreter in this preparation environment. Verify any adapted function on your own data before relying on it for a scientific result.

0.3 Related material

The accompanying teaching materials and additional R examples are available in the R-course GitHub repository and via the R programming page. These are optional resources: no chapter assumes that you have downloaded my private notes or the original code collection.

The full Base R / lattice / ggplot2 synopsis is included as a companion to Chapter 8. The complete bibliography and licence information are at the end of this script.

0.4 A recurring question

Before running unfamiliar code, ask yourself what kind of result it will return. A number? A vector? A list? A model object? Inspect the result with str(), class() or typeof(). That small habit often explains what initially appears mysterious in R.

1 Looking inside R objects

A surprising number of programming problems become easier once you know what kind of object you are working with. R stores numbers, character strings, data frames, fitted models and even functions as objects. The first skill is not to memorise advanced definitions; it is to ask R a few useful questions about an unfamiliar object.

1.1 Inspect before changing anything

x <- c(2, 5, 8, 11)          # a numeric vector

x                             # look at its values
length(x)                     # how many elements?
class(x)                      # broad class of the object
typeof(x)                     # underlying storage type
str(x)                        # short structural description

For a dataset, inspect its first few observations and its structure:

head(mtcars)                 # first six rows
names(mtcars)                # variable names
str(mtcars)                  # variables and their types
summary(mtcars$mpg)         # summary of fuel consumption

Do this before starting a statistical analysis. A variable may have been imported as text instead of numeric data, or a data frame may contain values that you did not expect.

1.2 Vectors, matrices and attributes

R matrices are a convenient example of how simple data can gain additional structure.

x <- 1:6
m <- matrix(x, nrow = 2)   # same six numbers, arranged in two rows

x
m
length(m)                   # six values
nrow(m)                     # two rows
ncol(m)                     # three columns
attributes(m)               # includes the dimensions

The dim attribute tells R that m is arranged as a matrix. Arithmetic operates on all its numbers while normally keeping this structure:

m + 1                       # add one to every matrix element
dim(m + 1)                  # dimensions remain 2 by 3
as.vector(m)                # turn the matrix into an ordinary vector

An attribute is additional information attached to an object: for example dimensions, names or a class. You do not have to manipulate attributes by hand to use R effectively, but inspecting them can explain otherwise mysterious behaviour.

1.3 Lists, data frames and the meaning of brackets

A data frame is built from columns, and different forms of indexing can produce different results:

d <- mtcars[1:3, c("mpg", "wt")]  # three rows, two columns

str(d)                        # inspect the result

d["mpg"]                      # a data frame with one column
d[["mpg"]]                    # the numeric values in that column
d$mpg                         # shorter way to extract those values

A useful rule of thumb: [ typically selects a subset and retains the container, whereas [[ extracts one component. For data frames, drop = FALSE keeps the result as a data frame when selecting a single column:

d[, "mpg"]                  # often a vector
d[, "mpg", drop = FALSE]    # definitely a one-column data frame

Why does that matter? A later function may expect a vector and fail if it receives a data frame, or vice versa. Inspect the result with class() or str() rather than guessing.

1.4 Operators are functions too

We usually write arithmetic with operators between two values:

3 + 5

But R also lets us call the addition operator by its name. Backticks allow us to refer to unusual function names, including operators:

`+`(3, 5)                   # same answer as 3 + 5
`*`(2, 4)                   # same answer as 2 * 4

Even the extraction operator can be written like an ordinary function call:

mtcars[2, 5]
`[`(mtcars, 2, 5)          # same row/column selection

At this stage, it is enough to recognise that these are equivalent ways of expressing an operation. In Chapter 4 we will use this idea to pass a function as an argument to another function. More advanced examples, including control-flow constructs and function types, appear after the necessary concepts have been introduced.

1.5 A small comparison: selecting one column

Task Code Result

The goal is not to memorise four expressions merely for their own sake. It is to understand that the structure of an object determines how you can use it later.

2 Control flow: conditions and loops

Imagine that you have to repeat the same calculation for ten variables. You could copy a line ten times, changing the variable name each time. But copying code is tedious and error-prone. A loop expresses the common pattern once. Before using loops, we need to understand the simple conditions that control them.

2.1 Making decisions with if and else

A condition answers a yes-or-no question. In R, the values are TRUE and FALSE (not strings in quotation marks).

age <- 20
age >= 18         # TRUE: the comparison produces a logical value

if (age >= 18) {
  print("adult")   # Executed when the condition is TRUE
} else {
  print("minor")   # Executed otherwise
}

An if condition must have exactly one logical result that is not missing. For a whole vector, ifelse() can make an element-wise choice:

ages <- c(16, 20, 35)
ifelse(ages >= 18, "adult", "minor")

This is not a universal replacement for if: the two are intended for different tasks. An ordinary if decides whether a block of code runs; ifelse() chooses values element by element.

2.2 Combining conditions: &, |, && and ||

A researcher may want observations that are at least 18 years old and have non-missing information. & means AND; | means OR. Both operate element by element on vectors.

ages <- c(16, 20, NA, 35)
ages >= 18                    # FALSE TRUE NA TRUE
!is.na(ages)                  # TRUE TRUE FALSE TRUE

selected <- !is.na(ages) & ages >= 18
selected                     # FALSE TRUE FALSE TRUE
ages[selected]               # 20 35

R also has && and ||, which are designed for single conditions. They use short-circuit evaluation: the second part is evaluated only when the first part does not already determine the answer.

FALSE && stop("Never evaluated")  # FALSE; the error does not occur
TRUE  || stop("Never evaluated")  # TRUE; the error does not occur

# In contrast, & and | evaluate both sides:
# FALSE & stop("This part IS evaluated")  # Error (run separately)

Here is a practical use. If x is empty, x[1] has no value. We must check its length before comparing its first element:

x <- numeric(0)                  # an empty numeric vector

if (length(x) > 0 && x[1] > 10) {
  print("The first value is larger than ten")
}

The second condition is skipped when x is empty. With &, both expressions would be evaluated, producing a length-zero result that cannot be used as the condition of if. Use &/| for filtering vectors, and usually &&/|| for scalar if conditions. Not every simple if needs multiple checks: add them only when they solve a realistic problem.

2.3 One task, four solutions: square the numbers 1 to 10

The task is deliberately simple so that we can concentrate on how each solution works rather than on the mathematics.

Solution A: for loop

for (i in 1:10) {
  print(i^2)         # i takes the values 1, 2, ..., 10
}

This prints the squares but does not save a convenient vector of results. We can fix that:

squares_for <- numeric(10)       # reserve space for 10 numbers

for (i in 1:10) {
  squares_for[i] <- i^2          # place each square at its position
}

squares_for                      # inspect the finished vector

The assignment inside the loop is the essential step. numeric(10) creates a numeric vector of length ten initially filled with zeros. Reserving the result in advance is a clear and efficient habit, especially for large loops.

Solution B: while loop

squares_while <- numeric(10)
i <- 1                           # initialise the counter

while (i <= 10) {                 # repeat while this condition is TRUE
  squares_while[i] <- i^2
  i <- i + 1                     # important: advance the counter
}

squares_while

A while loop is particularly suitable when the number of repetitions is not known beforehand, but the stopping condition is known. Forgetting to update i could result in an infinite loop.

Solution C: repeat with break

squares_repeat <- numeric(10)
i <- 1

repeat {
  squares_repeat[i] <- i^2
  if (i == 10) break             # exit explicitly after the tenth value
  i <- i + 1
}

squares_repeat

repeat has no condition in its header. A break statement inside the body determines when it ends. The position of break matters.

Solution D: vectorised arithmetic

squares_vector <- (1:10)^2      # R squares the whole vector at once
squares_vector

All four give the same ten numbers. For simple element-wise arithmetic, the last solution is easiest to read. But if every repetition involves several decisions, a simulation, or a fitted model, a loop may be preferable.

Approach When it is useful What to watch for
for Known sequence of items or repetitions Store results rather than just printing them
while Continue until a condition changes Make certain the condition can become FALSE
repeat Stopping rule is naturally placed inside the body Include an appropriate break
Vectorisation Same mathematical operation on many elements Not every algorithm can be expressed this way

2.4 1:length(x), seq_along(x) and seq_len(n)

You will see all three in real R code. For a known non-empty vector, 1:length(x) is perfectly understandable:

x <- c(5, 8, 12)
1:length(x)               # 1 2 3
seq_along(x)               # 1 2 3: same indices
seq_len(3)                 # 1 2 3: three indices

There is one important corner case:

x <- numeric(0)          # empty vector
1:length(x)               # 1 0 (not what we wanted)
seq_along(x)               # integer(0): no indices
seq_len(length(x))         # integer(0): same idea

Why? The colon operator makes a sequence between two endpoints. Since length(x) is zero, 1:0 contains the numbers 1 and 0. seq_along(x) instead means “the positions of the elements of x”, while seq_len(n) means “the first n positive positions”.

Practical judgement: if your script deliberately uses a checked, non-empty dataset, 1:length(x) will often be fine. If you write a reusable function that must also work for empty inputs, seq_along(x) expresses your intention more reliably. This is a reasoned choice, not a ban on one syntax.

You may also encounter 1L in code. It means the integer one, whereas 1 is normally a double-precision number:

typeof(1)       # "double"
typeof(1L)      # "integer"
1 + 1L          # 2: R handles the conversion automatically

For the examples in this chapter, ordinary 1 works just as well. The L suffix becomes useful when a function requires a specific integer type, but you do not need to add it to every counter.

2.5 Saving more complicated results

Vectors are suitable when each repetition returns one number. If each repetition returns an entire model, a list is more appropriate:

set.seed(5)
models <- vector("list", 3)       # create a list with three positions

for (i in 1:3) {
  y <- mtcars$mpg + rnorm(nrow(mtcars), sd = i)
  models[[i]] <- lm(y ~ mtcars$wt)  # store a complete model object
}

models[[1]]                       # inspect the first model
coef(models[[1]])                 # inspect its coefficients

A vector and a list solve different storage problems. The double brackets [[i]] extract or replace one list element, a topic introduced in Chapter 1.

3 Writing and improving your own functions

A researcher often starts with a calculation that works perfectly for one dataset. Later, the same calculation is needed for another variable, another project, or a colleague’s data. A function turns a one-off sequence of commands into a reusable operation.

The objective is not to write the most complicated function possible. We will begin with something that fits on one line and add features only when they solve a clearly defined problem.

3.1 From a calculation to a function

The mpg column in the built-in dataset mtcars reports miles per US gallon. We want to convert it to litres per 100 km. The conversion factor is approximately 235.215.

# One-off calculation for the first car:
235.215 / mtcars$mpg[1]

# The same operation for all cars:
235.215 / mtcars$mpg

# Give the calculation a name and an input argument:
mpg_to_l100 <- function(mpg) {
  235.215 / mpg
}

mpg_to_l100(30)            # convert one fuel-consumption value
mpg_to_l100(mtcars$mpg)    # convert an entire column

The function has three parts: a name (mpg_to_l100), an argument (mpg), and a body (235.215 / mpg). The last evaluated expression is returned automatically. We could add return(235.215 / mpg), but it is not required here.

There is no need for a loop. Division in R is already vectorised: if mpg is a vector, R divides the factor by each element. This makes the function both short and generally useful.

3.2 Changing the interface, one step at a time

Suppose we would like to change the conversion factor for some reason. An argument with a default value helps:

mpg_to_l100 <- function(mpg, factor = 235.215) {
  factor / mpg
}

mpg_to_l100(30)                # uses the default factor
mpg_to_l100(30, factor = 235)  # uses the specified factor

The caller need not provide factor unless a different value is wanted. This is a general pattern for optional arguments.

A function should ideally receive what it needs as arguments. Compare the following versions:

# Less reusable: assumes a particular object exists in the workspace.
convert_my_data <- function() {
  235.215 / mtcars$mpg
}

# More reusable: no dependence on that specific dataset.
mpg_to_l100 <- function(mpg) {
  235.215 / mpg
}

The second version can be used on any suitable vector, including one generated in a simulation or imported from another study.

3.3 What about invalid input?

A small teaching function does not need dozens of checks. But once the same function is used repeatedly, it can be helpful to give informative error messages. Start with one realistic question: what happens if somebody passes text instead of numbers?

mpg_to_l100 <- function(mpg) {
  if (!is.numeric(mpg)) {             # check the input type
    stop("Please supply numeric mpg values.")
  }

  if (any(mpg <= 0, na.rm = TRUE)) {  # reject zero and negative values
    stop("mpg must be greater than zero.")
  }

  235.215 / mpg                    # result; NA remains NA
}

mpg_to_l100(c(20, 25, NA))
# mpg_to_l100("twenty")             # uncomment to see the error

is.numeric(mpg) checks whether we have numeric data. The exclamation mark ! negates a logical result. any() asks whether at least one element meets a condition, and na.rm = TRUE prevents missing values from making the check itself indeterminate. This is an example of validation following the problem: rejecting zero mpg is justified by the conversion, while forbidding missing values would be a separate policy choice.

3.3.1 What is NA_real_ and do we need it?

The simple answer: usually not. NA already represents a missing value and works in the conversion above. R also supplies missing values of explicit types:

typeof(NA)          # "logical": the default type of NA
typeof(NA_real_)   # "double": a missing numeric (double) value
typeof(NA_integer_)# "integer": a missing integer value

c(3.5, NA)          # becomes a double vector; works normally
c(3.5, NA_real_)    # same numerical result here

R often converts NA to the required type automatically. An explicitly typed missing value is mainly useful in code with strict type requirements or when constructing a result whose type must be guaranteed. We will meet such cases later with vapply(). There is no reason to replace every NA with NA_real_ in ordinary analyses.

3.4 Case study: write a prime-number test

A prime number is an integer greater than 1 that has exactly two positive divisors: 1 and itself. The simplest implementation practically translates the definition into R:

is_prime <- function(x) sum(x %% (1:x) == 0) == 2

is_prime(2)    # TRUE
is_prime(7)    # TRUE
is_prime(8)    # FALSE
is_prime(1)    # FALSE

This uses three elementary ideas. 1:x creates possible divisors; x %% divisor gives the remainder; a remainder of zero means that the division is exact. sum() counts TRUE values as ones. If exactly two divisors are found, the result is TRUE.

Important limitation: this first function assumes a single positive integer. It is deliberately not a general-purpose implementation: x = 0, negative numbers, missing values, non-integers and vectors require further thought. Its virtue is that we can understand every part before making it more elaborate.

3.4.1 Improvement 1: define the domain

For a reusable function we can check that x is one finite whole number. We introduced the short-circuit operators || in Chapter 2; their use here ensures that an invalid type or length is rejected before subsequent comparisons are attempted.

is_prime_checked <- function(x) {
  # Is x a single numeric value?
  if (!is.numeric(x) || length(x) != 1) {
    stop("Supply one numeric value.")
  }

  # Exclude missing, infinite and non-integer values.
  if (is.na(x) || !is.finite(x) || x != floor(x)) {
    stop("Supply a finite whole number.")
  }

  if (x < 2) return(FALSE)     # 0, 1 and negative numbers are not prime
  sum(x %% (1:x) == 0) == 2   # reuse our original idea
}

is_prime_checked(7)
is_prime_checked(1)
# is_prime_checked(2.5)       # uncomment to see the error

This is longer than the one-liner, but not because a short function is somehow bad. We have added a new requirement: clear behaviour when the input is unsuitable. Note that floor(x) rounds down to the nearest whole number; comparing x with floor(x) therefore identifies non-integers.

3.4.2 Improvement 2: avoid unnecessary calculations

Testing every potential divisor up to x is wasteful. If x has a divisor larger than sqrt(x), the corresponding other divisor must be smaller than sqrt(x). Thus we only need to search up to the integer part of the square root.

For example, to decide whether 91 is prime, we do not need to test 1 through 91. Since sqrt(91) is about 9.54, the possible nontrivial small divisors are 2 through 9. We quickly find that 91 is divisible by 7.

is_prime_fast <- function(x) {
  # Step 1: check that the input is a single whole number.
  if (!is.numeric(x) || length(x) != 1) {
    stop("Supply one numeric value.")
  }
  if (is.na(x) || !is.finite(x) || x != floor(x)) {
    stop("Supply a finite whole number.")
  }

  # Step 2: handle the smallest numbers explicitly.
  if (x < 2) return(FALSE)  # 0, 1 and negatives
  if (x < 4) return(TRUE)   # 2 and 3

  # Step 3: look only for divisors no larger than sqrt(x).
  max_divisor <- floor(sqrt(x))
  for (divisor in 2:max_divisor) {
    if (x %% divisor == 0) return(FALSE)  # found a divisor
  }

  TRUE                     # none found: x is prime
}

is_prime_fast(91)          # FALSE
is_prime_fast(97)          # TRUE

Why the special case for 2 and 3? Without it, the expression 2:floor(sqrt(3)) becomes 2:1, which includes an unwanted value. We have deliberately handled the small boundary before starting the loop. For ordinary teaching-sized integers the procedure is appropriate; very large integers require additional numerical considerations.

3.4.3 Synopsis: what changed?

Version Improvement Remaining trade-off
One-liner Closely follows the mathematical definition Assumes a positive scalar integer
Checked version Rejects unsuitable inputs clearly Still tests many unnecessary divisors
Square-root version Stops early and searches fewer divisors More code and more boundary conditions

The goal is to understand why each modification was made. A function should not begin with its most complex implementation unless its readers already know the ideas it uses.

3.5 A useful small summary function

Suppose we need the mean and standard deviation of a variable, excluding missing observations. Start with the calculations separately:

x <- c(3, 5, 8, NA)
observed <- x[!is.na(x)]   # keep the non-missing values
mean(observed)
sd(observed)
length(observed)

Now gather them in one function:

summarise_measurements <- function(x) {
  observed <- x[!is.na(x)]       # remove missing observations

  n <- length(observed)          # number of observed values
  average <- mean(observed)      # arithmetic mean
  spread <- sd(observed)         # standard deviation

  c(n = n, mean = average, sd = spread)  # named result vector
}

summarise_measurements(c(3, 5, 8, NA))

We have not introduced elaborate type checks because the example is about building and returning a structured result. For an entirely missing vector, mean(numeric(0)) returns NaN and sd(numeric(0)) returns NA. If that is not the behaviour we want, we can add one explicit special case:

summarise_measurements <- function(x) {
  observed <- x[!is.na(x)]

  if (length(observed) == 0) {         # no observations left
    return(c(n = 0, mean = NA, sd = NA))
  }

  c(n = length(observed),
    mean = mean(observed),
    sd = sd(observed))
}

summarise_measurements(c(NA, NA))

This function is deliberately transparent. Later, when you write package functions or handle large heterogeneous datasets, you may want more formal validation. But it is more important that you can explain the calculation today.

3.6 Returning values instead of just printing them

print() displays information for a human reader. return() (or the final expression) gives a value to the caller, which can be saved and used in subsequent calculations:

square_and_print <- function(x) {
  print(x^2)
}

square <- function(x) {
  x^2
}

result <- square(5)
result + 10                 # 35: the value is available for further work

Here square_and_print() also returns the printed object in this particular example because print() returns it; nevertheless, explicitly separating calculation from display is a useful design principle. Chapter 5 explains what happens to intermediate objects created inside a function.

4 Thinking in functions: apply, Map and friends

A loop is not a problem to be eliminated. It is one way of saying “do the same sort of operation several times”. R also offers higher-order functions: functions that accept other functions as arguments. They can make repeated operations concise, especially when the results naturally belong in a list.

The key questions are: What varies from one repetition to the next? What stays fixed? What form should the result have?

4.1 Functions are objects: you can pass them to your own functions

You have probably written code such as mean(x) or summary(x) many times. In both cases, the name identifies a function and the parentheses tell R to call that function. But a function can also be stored in an object, just like a number or a dataset:

x <- c(2, 4, 6, 8)            # four numbers to summarise

my_statistic <- mean          # store the FUNCTION, without calling it
my_statistic(x)               # 5; same as mean(x)

my_statistic <- median        # now the same name refers to median()
my_statistic(x)               # 5; same as median(x)

Notice the difference between mean and mean(x): the first is a function object, while the second is a function call whose result is a number. This distinction makes a surprisingly useful programming technique possible: we can write a function that accepts another function as an argument.

4.1.1 A small function that accepts a function

Suppose we want to summarise a numeric vector, but we would like to choose how to summarise it when calling our function:

apply_statistic <- function(x, FUN, ...) {
  # x is the data we want to analyse.
  # FUN is the function we want to apply to those data.
  # ... passes optional additional arguments to FUN.
  FUN(x, ...)
}

values <- c(2, 4, 6, 8)

apply_statistic(values, mean)                       # 5
apply_statistic(values, range)                      # 2 and 8
apply_statistic(values, quantile, probs = c(.25, .75))

Nothing special happens to FUN: it is simply the name of an argument. When we write apply_statistic(values, mean), R assigns the function object mean to the argument FUN. The expression FUN(x, ...) then calls whichever function was supplied. We could also call this argument statistic or operation instead of FUN.

Why include the three dots (...)? Some functions require or allow additional arguments. For example, quantile() uses probs to select which quantiles to return. Without forwarding ..., the last call could not pass probs through our wrapper. If you wrote FUN(x) instead, R would ignore the arguments collected in ... rather than forwarding them.

4.1.2 A slightly more interesting example: simulate, then summarise

Now we can combine two steps. The following function first generates normally distributed random values and then lets the caller decide what should be calculated from them:

myfunction <- function(n, FUN, ...) {
  # 1. Generate n observations from a standard normal distribution.
  x <- rnorm(n, mean = 0, sd = 1)

  # 2. Apply the supplied function to the generated observations.
  #    Forward any further arguments (such as probs) using ...
  FUN(x, ...)
}

set.seed(123)                                    # reproducible random numbers
myfunction(n = 365, FUN = mean)                   # average
myfunction(n = 365, FUN = summary)                # several summary statistics
myfunction(n = 365, FUN = median)                 # median
myfunction(n = 365, FUN = quantile)               # default quantiles
myfunction(n = 365, FUN = quantile,
           probs = seq(0, 1, 0.2))              # quantiles at 0%, 20%, ..., 100%

This function is useful because we did not have to rewrite the simulation each time we wanted a different statistic. And the argument can be a function of our own creation, too:

range_width <- function(x) {
  # Difference between largest and smallest observation.
  max(x) - min(x)
}

myfunction(365, range_width)

One important detail: each call to myfunction() generates a new random sample. Consequently, the mean and median in the examples above are not calculated from exactly the same 365 values. If we specifically want to compare statistical summaries of one and the same sample, we should generate it once and reuse it:

set.seed(123)
sample_values <- rnorm(365)                 # generate one sample and save it

apply_statistic(sample_values, mean)        # mean of this sample
apply_statistic(sample_values, median)      # median of the SAME sample
apply_statistic(sample_values, sd)          # SD of the SAME sample

4.1.3 Why this matters for lapply() and Map()

We have just written a function that takes another function as input. That is the underlying idea of the so-called higher-order functions in R. For example, lapply(X, FUN) calls the supplied function once for each element of X, whereas Map() can pass several sets of arguments to that function position by position. They are not fundamentally mysterious: they are general-purpose tools built around the same simple idea.

The next sections show when those tools are convenient and when an ordinary loop is just as good.

Further reading: Hadley Wickham, Advanced R, chapter “Functions”, discusses functions as objects and the consequences of treating functions as first-class values.

4.2 From a loop to lapply()

Suppose we want the mean fuel consumption, weight and horsepower of the cars in mtcars.

measurements <- mtcars[c("mpg", "wt", "hp")]

# First approach: a straightforward for loop.
result_loop <- numeric(3)                # space for three means

for (i in 1:3) {
  result_loop[i] <- mean(measurements[[i]])
}

names(result_loop) <- names(measurements)
result_loop

We can also ask lapply() to call mean() on every column:

result_list <- lapply(measurements, mean)
result_list                                  # a list of three means

result_vector <- unlist(result_list)        # convert the list to a vector
result_vector

The general form is lapply(X, FUN): take every element of X, apply FUN to it, and collect the results in a list. The purpose is not speed at all costs; the purpose is to express the repeated operation clearly.

If we want a simplified result, sapply() often returns a vector:

sapply(measurements, mean)

For more controlled programming, vapply() specifies what each call must return:

vapply(measurements, mean, numeric(1))

Here numeric(1) is not input data. It is a template declaring that each call to mean() should produce exactly one numeric value. If a function unexpectedly returns two numbers or a character string, vapply() reports an error. This extra check can be useful in reusable code. A first-time learner can comfortably begin with for and lapply.

Construct Result Useful situation
for Whatever you explicitly construct Complex steps, branching, state or transparent iteration
lapply() Always a list Each iteration may return a model, vector or other object
sapply() Simplifies when possible Quick exploratory analysis
vapply() Predefined result type/shape Reusable functions where output consistency matters

4.3 Why and when use Map()?

lapply() iterates over one collection. Map() is particularly convenient when a function needs several arguments and we want to change two or more of them together. Think of matching a different sample size with a different mean for three simulations.

sample_sizes <- c(10, 20, 50)       # varying argument 1
means <- c(0, 5, 10)                # varying argument 2

set.seed(12)
samples <- Map(rnorm, sample_sizes, means)

length(samples)                     # 3 samples
sapply(samples, length)            # 10, 20 and 50 observations

The calls are paired position by position: rnorm(10, 0), then rnorm(20, 5), then rnorm(50, 10). Each result is a vector, so Map() returns a list.

4.3.1 Vary two arguments but keep a third fixed

Suppose all samples should have the same standard deviation. Instead of repeating sd = 2 three times, we can pass it once using MoreArgs:

set.seed(12)
samples <- Map(rnorm,
               sample_sizes,                    # n changes each time
               means,                           # mean changes each time
               MoreArgs = list(sd = 2))         # sd stays fixed

sapply(samples, sd)                  # sample SDs vary around 2

MoreArgs = list(sd = 2) is passed along to every call of rnorm(). That is often the most practical reason to use Map() or its relative mapply(): some inputs vary by iteration, others are fixed. We can express the same operation using a loop:

set.seed(12)
samples_loop <- vector("list", length(sample_sizes))

for (i in 1:length(sample_sizes)) {
  samples_loop[[i]] <- rnorm(sample_sizes[i],
                            mean = means[i],
                            sd = 2)
}

Both implementations are good. For three small simulations, the loop might be easier to follow; for a family of paired inputs, Map() shows the correspondence more directly. Be careful that the argument vectors are intentionally aligned. Map() can recycle shorter inputs rather than enforcing a matching research design, so check lengths when that matters.

4.3.2 Map() versus mapply()

Map() is a convenient wrapper around mapply() that always returns a list. By default, mapply() tries to simplify the result:

Map(`+`, 1:3, 10:12)     # list containing 11, 13, 15
mapply(`+`, 1:3, 10:12)  # numeric vector containing 11, 13, 15

In both cases, `+` is the addition function passed as a value. This connects to Chapter 1, where we saw that R operators are functions.

4.4 apply() for matrices and aggregate() for grouped data

Other members of the apply family solve different problems. For a numeric matrix, apply() can process rows or columns:

m <- matrix(1:12, nrow = 4)
apply(m, 2, mean)          # 2 means columns
apply(m, 1, sum)           # 1 means rows
colMeans(m)                # a direct specialised function

For grouped summary statistics, aggregate() is often simpler than constructing a loop:

aggregate(mpg ~ cyl, data = mtcars, FUN = mean)

These are not stylistic competitions. colMeans() is particularly direct for column means; aggregate() communicates grouping; Map() pairs varying arguments. Choose the construct that matches the task.

4.5 Reduce(): combine a collection into one result

Suppose several studies report the same variables in different datasets. We want to know which variable names occur in all studies.

study_variables <- list(
  c("age", "sex", "bmi"),
  c("age", "sex", "smoking"),
  c("age", "sex", "income")
)

intersect(study_variables[[1]], study_variables[[2]])
Reduce(intersect, study_variables)   # common to all three studies

Reduce() takes two elements, combines them, combines that result with the next, and continues. The same idea works with numbers:

Reduce(`+`, list(2, 3, 4))           # (2 + 3) + 4 = 9

There is no need to use Reduce() when sum(c(2, 3, 4)) is clearer. The function becomes interesting when you have many objects and a general rule for combining them.

4.6 Filtering collections with functions

You already know logical indexing:

x <- 1:10
x[x %% 2 == 0]                     # keep even numbers

For a list, Filter() can keep elements that meet a condition:

variables <- list(age = 1:10, sex = letters[1:5], weight = c(60, 80))
Filter(is.numeric, variables)      # keep numeric list elements

The argument is.numeric is itself a function. This is the essence of functional programming in R: functions can be supplied as data to other functions.

4.7 True vectorisation and Vectorize() are not the same

A function such as sqrt() already operates on a vector at once:

sqrt(1:5)                          # vectorised function

A function using scalar if works only on one value at a time:

odd_or_even <- function(x) {
  if (x %% 2 == 0) "even" else "odd"
}

odd_or_even(3)
# odd_or_even(1:5)                # not a suitable scalar call

Vectorize() can wrap it to accept a vector, but it works through repeated function calls and is not an automatic speed improvement:

odd_or_even_vector <- Vectorize(odd_or_even)
odd_or_even_vector(1:5)

# For this particular task, direct vector operations are simpler:
ifelse((1:5) %% 2 == 0, "even", "odd")

Again, the best implementation depends on the problem, not on whether one approach has a more sophisticated name.

4.8 A function can create another function: when is this useful?

Suppose we often classify laboratory measurements using a cutoff. One function takes two arguments:

above_cutoff <- function(x, cutoff) {
  x > cutoff
}

above_cutoff(c(10, 20, 40), cutoff = 25)

But what if we have fixed cutoff values for several analyses and want to avoid typing them repeatedly? We can create specialised functions with the cutoff already remembered:

make_above_cutoff <- function(cutoff) {
  function(x) {                   # this is the function we return
    x > cutoff                    # it remembers the chosen cutoff
  }
}

above_20 <- make_above_cutoff(20)
above_30 <- make_above_cutoff(30)

above_20(c(10, 25, 40))           # FALSE TRUE TRUE
above_30(c(10, 25, 40))           # FALSE FALSE TRUE

make_above_cutoff() is called a function factory: its output is another function. The output function remembers the environment where it was created, including the cutoff. This is called a closure and is explained in Chapter 5. You do not need a factory for every problem; it becomes useful when you create many related functions with fixed settings, or pass configured functions to other routines.

5 The workspace, function scope and environments

When you enter x <- 5 in the R console, where does x go? Why can you see it afterwards, but not necessarily see the variables created inside a function? And how can you find an object when you no longer remember its exact name? These are practical reasons to learn about R’s environments.

5.1 Finding objects in your workspace

The objects you create at the top level of an ordinary R session are normally stored in the global environment (.GlobalEnv), often called the workspace. You can list them using ls():

participants <- data.frame(age = c(20, 25, 33))
participant_count <- nrow(participants)
analysis_date <- "2026-11-25"

ls()                           # names of objects in the workspace

In a large analysis, you might have hundreds of objects and remember only part of a name. You can search the list using grep():

ls()[grep("artic", ls())]     # finds names containing "artic"
ls(pattern = "artic")         # a more direct way to do the same

grep(pattern, x) returns the positions of elements of x matching a pattern. The brackets then select those positions from the object-name vector. Here we use the fragment "artic" so it matches participants and participant_count.

Other useful commands are:

exists("participants")          # is an object with this name available?
get("participants")             # retrieve it using its name as text
class(participants)              # what sort of object is it?
str(participants)                # inspect its structure
ls.str()                         # list names and brief structures

These commands are particularly helpful when working with large, unfamiliar workspaces. ls() describes objects, not the variable names inside every data frame; use names(participants) for column names.

5.2 What happens to objects created inside functions?

Consider this ordinary function:

calculate_bmi <- function(weight, height_cm) {
  height_m <- height_cm / 100       # temporary local object
  bmi <- weight / height_m^2       # another local object
  bmi                             # return the result
}

my_bmi <- calculate_bmi(75, 180)
my_bmi

# height_m                          # error: not available here
# bmi                               # error: not available here

Objects created by <- inside the function are local to that function call. They do not automatically appear in your global workspace. This is extremely useful: a complicated analysis can generate many intermediate objects without cluttering your workspace with all of them.

More precisely, the local environment generally becomes eligible for garbage collection when the call finishes and nothing still refers to it. This does not guarantee that every byte of memory is immediately released. A returned function can also retain access to its enclosing environment, which we will see later.

return(bmi) would also work, but because bmi is the last expression, R returns it without an explicit return().

5.2.1 Returning several results

Suppose you want the BMI, the converted height and the original weight. You can return a list rather than creating three global variables from inside the function:

calculate_bmi <- function(weight, height_cm) {
  height_m <- height_cm / 100
  bmi <- weight / height_m^2

  list(bmi = bmi, height_m = height_m, weight = weight)
}

result <- calculate_bmi(75, 180)
result$bmi                        # access only the desired component
result$height_m

This is usually the cleanest way to make several results available to the caller.

5.3 Ordinary assignment and super assignment

We have already used <- to assign values. It creates or modifies a variable in the current environment. Inside a function that is usually the function’s local environment.

x <- 10

test <- function() {
  x <- 5
  print(x)
}

test()                   # prints 5
x                        # still 10

R also has super assignment, written <<-. Its effect is different: it looks for an existing variable in the enclosing environments and modifies the first one found. If none exists, R assigns in the global environment.

x <- 10

change_x <- function() {
  x <<- 5               # changes the enclosing x, not a local x
}

change_x()
x                        # now 5

This can be convenient but is also a source of unexpected side effects. If you simply want a result, returning it is usually clearer:

change_x_safely <- function() {
  5                      # give the value to the caller
}

x <- change_x_safely()    # caller decides where to store it

There is a third option: explicitly assign to a named environment using assign():

assign("new_value", 42, envir = .GlobalEnv)
new_value                # 42

This is most useful when you deliberately manage a set of objects by name. It is generally unnecessary for an ordinary calculation. In particular, <<- and assign(..., envir = .GlobalEnv) are not equivalent in every situation: <<- searches enclosing environments first.

5.4 What is an environment, and when might I create one?

An environment stores named objects, somewhat like a container. The global workspace is itself an environment. You can also make a separate environment when you want to collect related objects without placing each one directly in the global workspace:

results <- new.env()                  # create a fresh environment
results$mean_age <- 40
results$sample_size <- 100
results$description <- "pilot study"

ls(envir = results)                  # list names stored inside it
results$mean_age                     # retrieve one value

Why not just use a list? For most analysis results, a list is simpler and is usually the better choice. Environments have an additional property: they can be modified by reference. Two names referring to the same environment see the same changes:

same_results <- results               # another reference to the same environment
same_results$mean_age <- 41
results$mean_age                      # 41: it changed through the other name

This behaviour is useful for certain caches, shared state and advanced program structures. It can also make reasoning about changes harder. Creating environments is not necessary simply to write good R functions or statistical models.

5.4.1 Looking inside an environment with eapply()

You have seen lapply() for lists. eapply() applies a function to the objects stored in an environment and returns a list:

results <- new.env()
results$ages <- c(20, 40, 60)
results$group <- "A"
results$completed <- TRUE

ls(envir = results)              # names in the environment
eapply(results, class)           # class of each stored object
eapply(results, length)          # length of each stored object

The order of the returned list is not guaranteed to match the order you expect from the names. This is a helpful exploration tool, but it is not a reason to put all ordinary data analysis into environments.

5.5 Lexical scoping: where does R search for a name?

If a name cannot be found within the function call itself, R looks in the environment where the function was defined, then in that environment’s parent, and so on. This is called lexical scoping.

factor <- 2

multiply <- function(x) {
  x * factor            # factor is not a local variable or argument
}

multiply(10)             # 20
factor <- 3
multiply(10)             # 30: the outer variable has changed

The safer everyday design is to pass dependencies as explicit arguments:

multiply <- function(x, factor) {
  x * factor
}

multiply(10, 2)

Closures sometimes intentionally retain their enclosing variables. A function factory from Chapter 4 is an example:

make_multiplier <- function(factor) {
  function(x) x * factor
}

twice <- make_multiplier(2)
three_times <- make_multiplier(3)

twice(10)                  # 20
three_times(10)            # 30

Each returned function has access to its own factor. This is a practical reason to learn lexical scoping: it makes specialised functions possible without polluting the global workspace.

5.6 Lazy evaluation, and when force() actually matters

In ordinary R functions, arguments are lazily evaluated. This means that supplying an argument does not always evaluate its expression immediately. Instead, the value is calculated when it is first needed. In most day-to-day programs, this happens naturally and requires no special action.

ignore_second <- function(x, y) x
ignore_second(5, stop("Not evaluated"))  # returns 5: y is never used

So why does force() exist? Occasionally a function returns another function, and we need an argument to be evaluated now, rather than later when the returned function is called.

# A function factory WITHOUT force():
make_adder <- function(n) {
  function(x) x + n
}

# These functions are created in a loop:
adders <- vector("list", 3)
for (i in 1:3) {
  adders[[i]] <- make_adder(i)
}

sapply(adders, function(f) f(0))   # 3 3 3 (surprising!)

Why three threes? Each n is still waiting to evaluate the expression i. By the time we call the functions, the loop has finished and i is 3. Now force the argument during the factory call:

make_adder <- function(n) {
  force(n)                       # evaluate n immediately
  function(x) x + n
}

adders <- vector("list", 3)
for (i in 1:3) {
  adders[[i]] <- make_adder(i)
}

sapply(adders, function(f) f(0))   # 1 2 3 (as intended)

force(n) does not make the addition run sooner; it ensures that the argument used by the returned function has been evaluated at creation time. For a simple call like make_adder(5), both versions normally work. force() matters particularly when delayed evaluation interacts with changing variables, loops or other state.

6 Understanding objects, classes and methods

When R prints a fitted regression model, you do not see the same output as when it prints a data frame. Why? The answer involves classes and methods. You do not need to create your own class to benefit from this system, but understanding its basic mechanism helps enormously when exploring unfamiliar R objects.

6.1 Start with an ordinary model object

model <- lm(mpg ~ wt, data = mtcars)    # fit a linear regression

class(model)                           # "lm": the object's class
names(model)                           # names of its components
str(model, max.level = 1)              # inspect the structure

print(model)                           # concise model output
summary(model)                         # fuller statistical summary

lm() returns a list with additional class information. R uses the class to determine which printing or summary method should be applied. We can still examine the components in the familiar way:

model$coefficients                  # part of the underlying list
coef(model)                          # generic interface: often preferable
residuals(model)[1:5]               # first five residuals

This is an important practical reason to understand object classes. You can often use generic functions such as print(), summary(), coef() or plot() without knowing the complete internal structure of every model type.

6.2 A class is often just an attribute

We met attributes in Chapter 1. The class attribute tells many R functions how to treat an object.

x <- list(mean = 10, sd = 2)
class(x)                              # "list"

class(x) <- "my_summary"             # assign our own S3 class
class(x)                              # "my_summary"
str(x)                                # the underlying data are still there

No new object storage structure was required: we took a regular list and assigned a class name. This is the basis of R’s lightweight S3 object system.

6.3 The simplest possible S3 method

Imagine that, when printing my_summary objects, we would like to display only the mean in a friendly format.

# R's S3 naming convention is generic.classname.
print.my_summary <- function(x, ...) {
  cat("Mean:", x$mean, "\n")
}

print(x)                            # dispatches to print.my_summary()

There are only two new ideas. First, print() is a generic: its behaviour depends on the class of its argument. Second, R looks for a function whose name is constructed as print. plus the class name, here print.my_summary.

cat() writes text to the console. The special string "\n" starts a new line. The ... parameter allows the method to accept optional extra arguments in the generic interface; we do not need to use them in this tiny example.

If you want to see the underlying list without the custom display, try:

str(x)                               # inspect its contents
unclass(x)                           # view the object without its class
print.default(x)                     # use the default print method explicitly

This is enough to understand the central S3 idea. We can make constructors and validation more elaborate later, but they are not required to demonstrate method dispatch.

6.3.1 Compare ordinary printing with S3 printing

Expression Purpose
print(x) Selects the print method based on the class
print.my_summary(x) Calls our specific method explicitly
print.default(x) Calls the default printer rather than dispatching
str(x) Examines the internal structure
methods("print") Lists available print methods

6.4 When would you write your own S3 class?

Usually not when you only need a mean or a conversion. A normal function returning a number or a list is enough. An S3 class becomes attractive when a set of results belongs together and you want consistent behaviour for printing, plotting or summarising those results.

Most researchers will first encounter S3 as users of package objects. For instance, the same function coef() can obtain coefficients from multiple fitted model classes:

fit1 <- lm(mpg ~ wt, data = mtcars)
fit2 <- lm(mpg ~ wt + hp, data = mtcars)

coef(fit1)
coef(fit2)

As your own programs become more substantial, you might use the same mechanism to organise your result objects. But do not introduce a class merely to avoid returning an ordinary list.

6.5 What about S4, and why do some objects use @?

R also has the S4 system, which defines more formal classes with named slots. You may encounter S4 objects in specialised packages, including bioinformatics packages. A slot is often accessed using @:

# General S3/list-style component access:
# object$component

# S4 slot access (only if object is a suitable S4 instance):
# object@slot_name

This is not a universal rule that S3 objects use $ and all S4 objects must use @ for every operation. S4 classes can define methods for other operators, and some S4 objects also support $ or [ depending on their implementation. But knowing that @ is the standard slot-access operator is useful when a package returns an unfamiliar formal object.

For a first exploration of such an object, use class(object), str(object) and, if appropriate, methods::slotNames(object) rather than guessing its components.

6.6 For the curious: even if and for are functions

Now that we have seen functions, control flow and environments, one further feature of R becomes easier to appreciate. The usual if and for syntax can be written as calls to real R functions:

# Conventional syntax:
if (5 > 3) "yes" else "no"

# Equivalent call syntax:
`if`(5 > 3, "yes", "no")

# Conventional loop:
for (i in 1:3) print(i)

# Equivalent call syntax:
`for`(i, 1:3, print(i))

These are not merely function-like representations. They are calls to actual functions. However, if and for are not ordinary user-written functions. R identifies them as special primitives:

typeof(mean)       # "closure": an ordinary R function
typeof(sum)        # "builtin": an internal primitive
typeof(`if`)       # "special": a special primitive
typeof(`for`)      # "special"
is.function(`if`)  # TRUE

Why special? Unlike ordinary functions, whose arguments are managed through lazy evaluation, these primitives receive the expressions that make up their arguments and control when to evaluate them. An if evaluates only the chosen branch. A for evaluates its body repeatedly, each time with a new value of its loop variable.

You do not need these internals to use if or for. They are an interesting illustration of how consistently R treats functions as objects. See the R Core Team’s R Language Definition for a formal description.

7 Programming with statistical simulations

Simulation is one of the best ways to learn R as a programming language. We must create data, inspect them, repeat a calculation, save the results, and interpret the patterns. A simulation also makes a statistical idea visible in a way that a formula alone often cannot.

We will first work with the data-generation process itself. Never start an analysis by assuming that newly generated or imported data look the way you intended. Examine them.

7.1 Case study 1: sampling variability

Imagine a hypothetical population of adults whose ages follow a roughly bell-shaped distribution. We construct one in R, then look at it before drawing any samples.

set.seed(2026)                              # reproducible random numbers

population <- round(rnorm(100000,
                          mean = 55,        # intended centre
                          sd = 15))         # intended spread

# Keep only adult ages in a plausible range.
population <- population[population >= 18 & population <= 95]

length(population)                          # actual population size
summary(population)                         # minimum, quartiles, mean, maximum
sd(population)                              # variation between individuals

# First inspect the population graphically.
hist(population, breaks = 30,
     main = "Hypothetical population: ages",
     xlab = "Age in years")

The population is artificial; it does not represent observed German demographic data. Filtering changes its mean and standard deviation from those in the original rnorm() call. That is exactly why we inspect the data after generating and filtering them.

Now draw one random sample:

sample1 <- sample(population, size = 100, replace = TRUE)

summary(sample1)                              # inspect the sample
hist(sample1, breaks = 15,
     main = "One sample of 100 people",
     xlab = "Age in years")

mean(sample1)                                 # sample mean
mean(population)                              # population mean

The two means are unlikely to be identical. That is sampling variability.

7.2 Repeat the sampling process using a loop

One sample does not tell us much about the distribution of sample means. Let us repeat the same procedure 1,000 times and save each mean.

set.seed(7)
B <- 1000                          # number of simulated studies
n <- 100                           # people per study

sample_means <- numeric(B)         # reserve space for all 1,000 means

for (i in 1:B) {
  # Draw a fresh random sample of 100 observations.
  one_sample <- sample(population, size = n, replace = TRUE)

  # Store that sample's mean in position i.
  sample_means[i] <- mean(one_sample)
}

head(sample_means)                # inspect the first six results
summary(sample_means)             # inspect their distribution

hist(sample_means, breaks = 30,
     main = "Sampling distribution of the mean",
     xlab = "Mean age across 100 observations")
abline(v = mean(population), col = "red", lwd = 2)

The histogram shows the sampling distribution of the mean. Its centre should be close to the population mean; its spread is the standard error of the sample mean.

sd(population)                   # standard deviation of individual ages
sd(sample_means)                 # empirical standard error of the mean
sd(population) / sqrt(n)         # approximate theoretical standard error

Notice that sd(population) and sd(sample_means) describe different sources of variation. The first concerns individual people; the second concerns estimates from repeated samples of size n. Increasing n typically makes the sampling distribution narrower.

7.3 The same simulation using replicate()

replicate() repeats an expression a specified number of times. We can replace the explicit loop while keeping the essential idea unchanged:

set.seed(7)                      # restart random sequence for comparison

sample_means_rep <- replicate(B, {
  one_sample <- sample(population, size = n, replace = TRUE)
  mean(one_sample)
})

head(sample_means_rep)
summary(sample_means_rep)

# Compare the results. With the same seed and sampling calls,
# the two methods should produce the same sequence.
all.equal(sample_means, sample_means_rep)

all.equal() asks whether two results are equal up to numerical tolerance. Here, because the random-number sequence and operations are the same, the result should be TRUE. You do not need stopifnot(identical(...)) merely to learn from the simulation.

Synopsis: use a for loop when you want explicit control or need several intermediate steps. Use replicate() when the essential operation is “repeat this experiment B times”. Neither replaces the need to inspect the generated data.

7.4 Case study 2: confidence interval coverage

A 95% confidence-interval procedure is designed to cover the population parameter in about 95% of repeated samples under its assumptions. We can investigate its coverage by simulation.

First define a small function for one sample:

one_interval <- function(data, n) {
  x <- sample(data, size = n, replace = TRUE)

  estimate <- mean(x)                       # sample mean
  se <- sd(x) / sqrt(n)                     # estimated standard error
  margin <- qt(0.975, df = n - 1) * se      # two-sided t critical value

  c(lower = estimate - margin,
    upper = estimate + margin)              # return both limits
}

one_interval(population, n = 100)

Now repeat the function and check which intervals include the known population mean:

set.seed(18)
intervals <- replicate(1000, one_interval(population, n = 100))

# Rows are lower/upper endpoints; columns are simulated studies.
dim(intervals)
intervals[, 1:3]                            # look at the first three intervals

true_mean <- mean(population)
covered <- intervals["lower", ] <= true_mean &
           intervals["upper", ] >= true_mean

mean(covered)                               # simulated coverage proportion

The exact proportion changes between runs because we use a finite number of simulations. The calculation concerns the long-run behaviour of a method; it is not the probability that the fixed parameter lies in a particular observed interval. The t interval here is approximate for our synthetic, bounded population.

7.5 Case study 3: bootstrap a mean

The bootstrap estimates the sampling variability of a statistic by repeatedly drawing with replacement from the observed sample. Here the observed sample is the mpg variable in mtcars.

x <- mtcars$mpg
length(x)
hist(x, main = "Observed fuel consumption", xlab = "Miles per US gallon")

set.seed(21)
B <- 2000
boot_means <- numeric(B)

for (i in 1:B) {
  resample <- sample(x, size = length(x), replace = TRUE)
  boot_means[i] <- mean(resample)
}

hist(boot_means, breaks = 35,
     main = "Bootstrap means", xlab = "Resampled mean mpg")

quantile(boot_means, c(0.025, 0.975))  # simple percentile confidence interval

This is the basic nonparametric bootstrap for independent observations. The percentile interval is easy to teach but not universally optimal. Skewed statistics, clustering, longitudinal dependence or small samples may require different resampling schemes and interval methods.

We can express the same idea using replicate():

set.seed(21)
boot_means_rep <- replicate(B, {
  resample <- sample(x, size = length(x), replace = TRUE)
  mean(resample)
})

summary(boot_means_rep)

For more demanding work, R’s boot package provides established tools:

# Optional example; requires package "boot".
mean_stat <- function(data, indices) {
  mean(data[indices])        # indices identify the bootstrap sample
}

# result <- boot::boot(data = x, statistic = mean_stat, R = 2000)
# boot::boot.ci(result, type = c("perc", "bca"))

The point is not that manually coded bootstrapping is inherently superior. Doing it yourself once teaches what the package is doing, and makes it easier to spot a mistakenly designed resampling procedure.

7.6 Case study 4: fit related regression models

Suppose we want similar models with different response variables. A manual approach is acceptable for two models:

model_mpg <- lm(mpg ~ wt + hp, data = mtcars)
model_qsec <- lm(qsec ~ wt + hp, data = mtcars)

With many outcomes, copying and changing each call becomes error-prone. R formulas can be built from variable names using reformulate():

fit_outcome <- function(outcome, data, predictors) {
  # Construct a formula such as mpg ~ wt + hp.
  formula <- reformulate(predictors, response = outcome)

  # Fit the model and return it to the caller.
  lm(formula, data = data)
}

fit_outcome("mpg", mtcars, c("wt", "hp"))

The same function can now be called repeatedly:

outcomes <- c("mpg", "qsec")

models <- Map(fit_outcome, outcomes,
              MoreArgs = list(data = mtcars,
                              predictors = c("wt", "hp")))

names(models) <- outcomes
lapply(models, coef)             # extract coefficients from both models

This is a concrete example of Map() from Chapter 4: the outcome changes with each iteration, while the dataset and predictors remain fixed. We return complete model objects in a list so that each one can be inspected later. Dynamic model formulas are usually better constructed with reformulate() than by turning arbitrary text into R code with eval(parse(...)).

8 Graphics as a synopsis: Base R, lattice and ggplot2

A graphic is not only an image; it is the result of a programming interface. Three graphics systems can display similar statistical information while embodying very different ideas about how a plot is specified. The full 12-task, side-by-side code-and-figure comparison is included as a companion HTML document and editable .Rmd source. The examples below focus on three useful tasks.

When comparing systems, use the same data, grouping variables, histogram breaks and model predictions to make the comparison fair. That is an important methodological lesson: if we compare plotting systems, we should not confuse differences in syntax with differences in statistical calculation.

8.1 Three ways of thinking about a plot

  • Base graphics: a plotting call starts a figure; subsequent calls such as points(), lines() or abline() modify the current graphics device.
  • lattice: a formula specifies the relationship, often together with conditioning variables; a trellis object represents the plot.
  • ggplot2: data, aesthetic mappings and geometric layers are combined using + to build a plot object.

The interfaces can produce similar pictures without requiring equivalent internal machinery. Base R’s graphics package is included with R; lattice is a recommended package and ggplot2 is an additional package.

8.2 Synopsis 1: a simple scatterplot

cars <- mtcars

# Base R
plot(mpg ~ wt, data = cars,
     xlab = "Weight (1,000 lbs)", ylab = "Miles per gallon")

# lattice
lattice::xyplot(mpg ~ wt, data = cars,
                xlab = "Weight (1,000 lbs)", ylab = "Miles per gallon")

# ggplot2
ggplot2::ggplot(cars, ggplot2::aes(wt, mpg)) +
  ggplot2::geom_point() +
  ggplot2::labs(x = "Weight (1,000 lbs)", y = "Miles per gallon")

In Base R we first issue a drawing command. In lattice, we describe a relationship using a formula; to add complicated elements, we typically use panel functions. In ggplot2, the mapping belongs to aes() while points come from a geometry layer. Understanding these patterns makes new plotting tasks easier to transfer between systems.

8.3 Synopsis 2: conditioning on a categorical variable

Conditional plots are where the differences become especially apparent. For each transmission type we want one panel, with comparable axes.

cars$am <- factor(cars$am, levels = c(0, 1),
                  labels = c("Automatic", "Manual"))

# Base graphics: explicit loop and layout
oldpar <- par(mfrow = c(1, 2))
for (g in levels(cars$am)) {
  d <- subset(cars, am == g)
  plot(mpg ~ wt, data = d,
       xlim = range(cars$wt), ylim = range(cars$mpg),
       main = g)
}
par(oldpar)

# lattice: conditioning in the formula
lattice::xyplot(mpg ~ wt | am, data = cars)

# ggplot2: faceting is an added component
ggplot2::ggplot(cars, ggplot2::aes(wt, mpg)) +
  ggplot2::geom_point() +
  ggplot2::facet_wrap(~ am)

The methods solve a recognisably similar problem, but their defaults and panel layouts may differ. In a genuine methodological comparison, explicitly inspect axis limits, scales, missing-data handling and the ordering of categories.

8.4 Synopsis 3: a fitted line and a confidence interval

Here a visual comparison can accidentally become a statistical comparison if each system computes its own smoother. This comparison avoids this problem by fitting one linear model and passing the same predictions and pointwise confidence limits to all three systems.

fit <- lm(mpg ~ wt, data = cars)
pred <- data.frame(wt = seq(min(cars$wt), max(cars$wt),
                            length.out = 200))
pred <- cbind(pred, as.data.frame(
  predict(fit, newdata = pred,
          interval = "confidence", level = 0.95)))

# Base: plot, polygon, points, lines
plot(mpg ~ wt, data = cars, type = "n")
polygon(c(pred$wt, rev(pred$wt)),
        c(pred$lwr, rev(pred$upr)), col = "grey85", border = NA)
points(mpg ~ wt, data = cars)
lines(pred$wt, pred$fit, col = "red", lwd = 2)

# ggplot2: ribbon, points and line (lattice version in companion)
ggplot2::ggplot(cars, ggplot2::aes(wt, mpg)) +
  ggplot2::geom_ribbon(data = pred,
      ggplot2::aes(x = wt, ymin = lwr, ymax = upr),
      inherit.aes = FALSE, fill = "grey80") +
  ggplot2::geom_point() +
  ggplot2::geom_line(data = pred,
      ggplot2::aes(x = wt, y = fit),
      inherit.aes = FALSE, colour = "red")

Statistical distinction: the shaded interval in this example is a pointwise 95% confidence interval for the conditional mean, not a prediction interval for an individual observation and not a simultaneous 95% band for the entire line. The code used to calculate pred makes that distinction inspectable.

9 Becoming a better R programmer

A program that produces the right answer once is a useful beginning. A program that you can understand, verify and reuse months later is much more valuable. Better code is not necessarily shorter, more “functional”, or packed with defensive checks. It is code whose purpose, assumptions and outputs are clear.

9.1 First describe the task

Suppose you want the mean miles per gallon for each cylinder group in mtcars. That is the problem statement. Only then do we choose an implementation.

# First inspect the relevant variables.
head(mtcars[c("mpg", "cyl")])
table(mtcars$cyl)

# Base R: a direct grouped summary.
aggregate(mpg ~ cyl, data = mtcars, FUN = mean)

# A different base R route: split the values, then calculate means.
groups <- split(mtcars$mpg, mtcars$cyl)
lapply(groups, mean)

The two approaches compute the same means but return objects of different structures. aggregate() returns a data frame, while lapply() returns a list. Choose the return form that will make the next step easiest.

9.2 Base R versus dplyr: different styles, not a competition

For a longer chain of data-processing operations, dplyr can offer a readable alternative:

# Optional: run after installing the dplyr package.
# library(dplyr)
# mtcars |>
#   group_by(cyl) |>
#   summarise(mean_mpg = mean(mpg), .groups = "drop")

There is no obligation to use an additional package for a calculation already expressed clearly by one base R call. Conversely, a multi-step grouped data workflow may be easier to follow with verbs such as filter(), group_by() and summarise(). Both styles deserve to be understood; neither is universally preferable.

9.3 Explore first, then process

Before fitting a statistical model or running a simulation, check what is in the data:

str(mtcars)                    # variable types and structure
summary(mtcars$mpg)           # basic descriptive statistics
sum(is.na(mtcars$mpg))        # count missing values
hist(mtcars$mpg, breaks = 10,
     main = "Fuel consumption in mtcars",
     xlab = "Miles per US gallon")

An impressive model cannot compensate for a dataset where missing values, factor levels, coding mistakes or outliers were never checked.

9.4 Comments: explain what happens and why

For readers learning R, short explanations of what each line does are often essential. More experienced readers also appreciate explanations of why a particular choice was made. Good teaching code can use both.

set.seed(9)                         # reproducible simulation
means <- numeric(100)               # save 100 simulated means

for (i in 1:100) {
  # Draw one sample of 30 normally distributed observations.
  x <- rnorm(30, mean = 10, sd = 2)

  # Save its mean; the next iteration creates another sample.
  means[i] <- mean(x)
}

hist(means)                          # inspect the sampling distribution

Once students understand the loop, comments can become shorter. In a reference manual, the “why” might dominate; in a teaching script, the “what” and “how” also matter.

9.5 eval(parse(...)): what does it do, and when is it useful?

R can treat a string as text or convert it into an expression to execute. Two functions are involved:

text <- "sqrt(9) + 2"

parsed <- parse(text = text)         # turn a string into an R expression
parsed                              # inspect the expression
eval(parsed)                         # execute it: result is 5

# Both steps can be combined:
eval(parse(text = "sqrt(9) + 2"))

This is genuinely useful when executing R code provided as code in text form is the task. For example, an interactive experiment may deliberately accept an R expression from a trusted researcher, or you might inspect and evaluate a program fragment stored in a file. The important qualification is that eval(parse(...)) executes arbitrary R code: never use it on text supplied by an untrusted source.

Most ordinary data operations need something simpler:

# You know the name of an object as a string:
object_name <- "mtcars"
get(object_name)                      # retrieve an existing object

# You want to fit a model based on variable names:
f <- reformulate(c("wt", "hp"), response = "mpg")
lm(f, data = mtcars)

Here get() retrieves an object by its name and reformulate() builds a formula. Neither requires us to turn an arbitrary character string into executable R code.

Creating hundreds of separately named objects with assign() and then retrieving them through eval(parse(...)) is possible, but it is a poor default storage strategy. A list is usually easier to inspect and iterate over. This point belongs after the reader has seen what assign(), get() and eval(parse(...)) actually do, not before.

9.6 A practical way to check your own functions

Start with ordinary examples, then test a few boundaries. For the improved prime-number function from Chapter 3, try:

is_prime_fast(2)         # should be TRUE
is_prime_fast(3)         # should be TRUE
is_prime_fast(9)         # should be FALSE
is_prime_fast(97)        # should be TRUE

# Test an invalid input deliberately:
# is_prime_fast(2.5)      # should produce an informative error

You do not need a testing package to develop this habit. In larger projects, automated tests become worthwhile. all.equal() compares results, stopifnot() can enforce conditions, and the testthat package provides a fuller testing framework. Introduce these tools when there is a clear reason to automate checks, rather than filling the first examples with test machinery.

9.7 Measure performance only after getting the correct result

An explicit for loop may be slower than a direct vector operation. Whether this matters depends on the size of the task and the work done in each iteration.

x <- seq(0, 1, length.out = 100000)

# Transparent loop version.
squares_loop <- function(x) {
  result <- numeric(length(x))
  for (i in seq_along(x)) {
    result[i] <- x[i]^2
  }
  result
}

# Direct vector operation.
squares_vector <- function(x) {
  x^2
}

system.time(squares_loop(x))        # elapsed time for the loop
system.time(squares_vector(x))      # elapsed time for vector arithmetic

Time comparisons depend on hardware, the R version and the amount of work. Repeat benchmarks when differences are small. Do not add parallel processing just because it sounds advanced: creating workers, sending data and collecting results also costs time.

9.8 A few habits worth adopting

  • Prefer self-contained examples over scripts that assume dozens of hidden workspace objects.
  • Avoid personal absolute file paths in published code; use project-relative paths.
  • Prefer TRUE and FALSE to T and F, because the short names can be reassigned.
  • Use data = arguments or explicit column extraction rather than attach() when ambiguity might arise.
  • Do not insert rm(list = ls()) into a published script: it can delete objects a reader wishes to keep.
  • Keep analyses reproducible: report the origin of data, random seeds and relevant dependencies.
  • Prefer a straightforward solution that readers understand to an impressive-looking solution they cannot maintain.
